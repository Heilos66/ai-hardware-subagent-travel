# 原 RAGFlow 与 AME 知识库效果对比

AME 是当前小知识库的低时延候选，但现有证据不足以认定检索质量无损、全面优于原 RAGFlow 或已满足 AgentArts 线上 P95 小于 100ms。它替换了检索方式：原方案为 RAGFlow + CSS + MaaS embedding/rerank，新镜像为容器内 AME graph 本地检索。

## 比较范围与测试条件

这里“原知识库”指有完整归档的 2026-10-21 RAGFlow + CSS 测试，分别保留 32、8 个重排候选；不是早期口头报告的 200–300ms，也不是当前 AgentArts 的实时测量。AME 是 2026-10-26 的 graph 带词典方案，与新镜像使用相同检索实现和 52 个固定片段。

| 条件 | 原 RAGFlow | AME |
|---|---|---|
| 语料 | 4份文档，52片段 | 复用相同片段正文与ID |
| 问题 | 20个，多数明确含文物名 | 相同20问；另有12个探索改述和2个库外问题 |
| 机器 | AMD64 ECS | 开发者Mac ARM64 |
| 调用 | ECS本机调用服务；CSS及MaaS在远端 | 本机回环HTTP；另测实际Java客户端 |
| 并发 | 1，完成后间隔至少60秒 | 1，常驻内存，连续调用 |
| 次数 | 每种配置20次正式请求 | HTTP 200次；Java 200次；引擎1000次 |
| 结果 | 最多5片段，阈值0.2 | 最多5片段，适配接口阈值0，分数不与原方案等价 |
| 模型 | 公网bge-m3 + bge-reranker-v2-m3 | 本地哈希向量、词法/图扩散及评分，无远程模型 |
| 最终LLM生成 | 不计入 | 不计入 |

本次重新分析既有逐请求记录，没有发起线上模型压测。重复请求只增加时延样本，质量仍按20个独立问题计算。跨机器、跨时间、跨算法，不计算框架加速倍数或优化百分比。

## 调用时延

单位ms，分位数为nearest rank。

| 方案与边界 | 样本数 | P50 | P95 | 最大值 | 小于100ms |
|---|---:|---:|---:|---:|---:|
| 原RAGFlow，32候选，检索API | 20 | 1069.79 | 4109.11 | 7893.47 | 0/20 |
| 原RAGFlow，8候选，检索API | 20 | 511.91 | 5269.14 | 10490.70 | 0/20 |
| AME，本地兼容HTTP | 200 | 7.50 | 9.37 | 10.70 | 200/200 |
| AME，Java客户端到解析完成 | 200 | 8.67 | 10.28 | 11.62 | 200/200 |

原方案20次全部API成功，但每种配置有1个空结果，表中保留这次调用，不通过删除空结果改善统计。原方案20样本P95为排序第19项，无法代表稳定长尾水平。AME尚无AgentArts网关、冷启动、多实例和并发情况下的线上P95。

### 各阶段

| 阶段 P50 / P95 ms | 原32候选 | 原8候选 | AME |
|---|---:|---:|---|
| embedding调用 | 141.04 / 172.44 | 153.01 / 189.52 | 无远程embedding；本地特征处理包含在recall |
| CSS搜索 | 27.66 / 32.07 | 12.77 / 15.57 | 不调用CSS |
| MaaS rerank调用 | 818.44 / 3874.25 | 285.13 / 5078.80 | 不调用MaaS；本地评分包含在recall |
| 其余服务端耗时 | 73.42 / 76.08 | 35.71 / 41.11 | 未拆成完全相同阶段 |
| AME引擎recall整体 | — | — | 7.09 / 8.97（1000次） |

MaaS阶段含公网、SDK及服务处理，不是纯GPU推理。各阶段分位数不可相加。原记录中模型调用占据主要时间；AME通过取消这两次远程调用改变了时延结构，并不是用C++把同样两次模型调用压到10ms。

## 检索质量

### 文档命中与上下文

| 指标（按20个独立问题） | 原32候选 | 原8候选 | AME |
|---|---:|---:|---:|
| 首条命中目标文档 | 19/20 | 19/20 | 20/20 |
| Top5包含目标文档 | 19/20 | 19/20 | 20/20 |
| 非空结果 | 19/20 | 19/20 | 20/20 |
| 返回片段总数 | 90 | 89 | 100 |
| 目标文档片段数 / 全部返回片段 | 88/90（97.8%） | 88/89（98.9%） | 91/100（91.0%） |
| 每问返回正文平均字符数 | 2202.7 | 2273.9 | 2270.1 |

片段所属文档比例不是语义Precision：其他文档也可能提供有用证据，例如兵马俑文档讨论唐三彩工艺。AME混入其他文档更多，是否为噪声需要按问题标注。字符数含HTML等原始文本，不是模型Token数，也不代表Java截断后的最终Prompt。

原两配置均在“参观兵马俑需要注意哪些文物保护问题？”返回空结果。AME返回5片段，但首条是兵马俑基本信息表，只列“彩绘保护”等关键词；不能仅凭非空就判定已经充分回答文物保护问题。

AME的20问在10次重复中Top5片段ID及排序一致。原方案每题只测1次，不能据此判断哪套排序更稳定。

### 答案证据排序抽查

以下通过返回正文的明确答案词核对首次出现位置，不是完整金标，不对其计算整体答案准确率。需保留否定、实体和上下文语义。

| 问题及检查词 | 原32候选 | 原8候选 | AME |
|---|---:|---:|---:|
| 长信宫灯收藏单位：河北博物院 | 第3条 | 第3条 | 第1条 |
| 长信宫灯出土地：满城 | 第1条 | 第1条 | 第1条 |

| 兵马俑发现时间：1974 | 第1条 | 第1条 | 第2条 |
| 三彩是否只有三色：正文的明确否定说明 | 第1条 | 第1条 | 第1条 |
| 载乐骆驼俑材料：釉陶 | 第1条 | 第1条 | 第1条 |
| 人面具时代：商代后期 | 第1条 | 第1条 | 第1条 |

AME在收藏单位问题上排序更好，在材料、发现时间问题上排序退后。当前Top5仍能提供这些明确证据，不建议仅凭首条文档命中率100%就把TopK降为1。

### 泛化与无答案

AME额外12个描述/器号改述问题首条文档12/12命中，但问题根据已知语料编写，并非盲测；原RAGFlow没有该组对照数据，不能宣称AME改述能力更强。

天气、车票两个库外问题，AME都返回5个文物片段。当前阈值0无法有效阻断此类结果；它不意味着LLM一定答错，但引入无关证据的风险已实际观察到。原方案没有这两题的对应结果，不能断言原方案一定能够正确拒答。

最终回答正确率、忠实性、歧义消解、跨文档证据完整性，以及答案级Recall、MRR、nDCG均未完成金标评估。镜像冒烟测试用的是模拟对话模型，只证明真实检索内容进入提示词，不证明真实模型回答正确。

## 部署与使用差异

| 维度 | 原RAGFlow + CSS | 本次AME镜像 |
|---|---|---|
| 更新知识 | 独立知识库服务更新 | 固定语料打入镜像，当前更新需重新构建发布 |
| 在线依赖 | CSS、MaaS及网络 | 检索仅依赖本容器；最终对话模型仍联网 |
| 冷启动 | 本组没有测完整服务启动 | Mac上词典及导入约14.7秒，另加Java启动；云端需实测 |
| 并发 | 本组仅测单并发 | HTTP可接多请求，worker由锁串行执行；并发可能排队 |
| 多实例 | 共享独立知识库后端 | 每个容器各自加载语料和索引；更新需确保版本一致 |
| 管理功能 | 原知识库独立管理 | 当前适配器无上传UI、增量同步、多租户权限功能 |
| 费用 | 每次请求调用embedding/rerank并使用CSS | 检索取消这些调用；新增常驻内存和冷启动成本，未量化总费用 |
| 日志 | Java阶段日志及原服务细分阶段 | Java接口保留；适配器返回recall时间，但需核对线上日志是否采集该字段 |
| 约束匹配 | 保留CSS、MaaS rerank | 当前方案不保留在线CSS/MaaS rerank |

## 判断与下一步验收

目前适合在AgentArts单独运行时试用AME并保留原知识库回退。对于固定、较小的文旅语料，它已展现低延迟潜力；还不能直接替换生产方案并宣布质量等价。

正式对比建议在同一AgentArts资源规格、同一客户端与时段交替测试两版，固定语料版本、Top5、最终对话模型和提示词。分别测暖机检索、网关到检索结果、完整Agent首字及总耗时；并发1/5/10，记录所有失败和重试。原方案限流时记录限流本身，另做低速质量评测，不能只保留成功请求。

质量建议使用不少于100个不同问题，覆盖明确实体、改述、歧义、跨文档、细节、无答案和时效问题；由业务侧标注支持答案的片段及必要事实。以答案证据Top5覆盖、错误实体率、无答案处理和实际回答正确率为准。质量容忍度须由业务确定；历史P95小于100ms目标仍以线上验收口径为准。
